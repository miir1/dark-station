## 2. 어떤 방향이어도 지켜야 할 기술 제약

1. 순수 브라우저 JS(ES2020), 빌드·번들러·npm 의존 없음. `<script>` 나열 순서가 곧 모듈 순서.
2. GitHub Pages 정적 호스팅: 서버 코드 없음, 파일은 상대 경로, 배포는 `bump → deploy.bat` 2단계 유지.
3. PC 웹 우선: 논리 640×360 정수 배율, 키보드(WASD/Space/Esc/Tab/숫자)+마우스. 폰은 깨지지 않을 정도만.
4. 상태는 **함수 없는 순수 JSON** 하나. 난수 상태 포함. `JSON.stringify`로 저장·비교·테스트가 다 된다.
5. 저장: localStorage + 저장 코드(base64). `v` 버전 필드 필수, 옛 저장은 변환하거나 거부(절대 깨진 채 열지 않음).
6. 규칙 엔진은 화면 없이 Node에서 돈다(테스트·봇의 전제). DOM·canvas·setTimeout을 엔진에 넣지 않는다.
7. 성능: 자산 총량 ≤ 5MB, 첫 화면 ≤ 2초, 60fps 불필요(턴제) — 지도 그리기는 `requestAnimationFrame` 1개만.
8. 한글 처리: 조사 `J(name,'이/가')`, 이름 치환 `{who:이/가}`, 글은 데이터에만 둔다(코드 안 한국어 문장 금지).
9. 복잡도 상한: 파일 1개 ≤ 600줄, 함수 ≤ 60줄, 모듈 ≤ 10개. 디렉터가 파일 이름만 보고 "어디를 고치나"를 알 수 있어야 한다.
10. 모든 조작은 `dispatch` 한 문으로. 화면이 상태를 직접 고치지 않는다(지금 v3가 `setFlag`로 깃발을 세우는 것이 상한선).

## 3. 아키텍처 제안 2안

| 항목 | A안: 현 엔진 유지, 데이터·화면만 교체 | B안: 데이터 주도 엔진 새로 짜기 |
|---|---|---|
| 무엇을 하나 | engine.js 틀은 두고 규칙 함수(아침·원정·저녁·밤·승차)를 새 GDD에 맞춰 고친다. data.js는 새로 쓴다. game.js는 흐름만 다시 쓴다 | 엔진은 **해석기**: 페이즈·사건·판정·효과를 JSON/표(`data/*.json`)에서 읽어 실행한다. 규칙 수치·사건·분기·대사는 전부 데이터. 코드는 "표를 읽는 법"만 안다 |
| 장점 | 빠르다. 테스트 53·봇·저장이 거의 그대로 산다. 검증된 코드가 많다 | 세계관·스토리·수치가 바뀌어도 **코드를 안 고친다**. 기반설계·텍스트 에디터가 표만 고친다. 문장 검사·용어 통일·길이 검사를 표에 바로 돌릴 수 있다. 밸런스 봇이 표를 자동으로 바꿔 가며 돌릴 수 있다 |
| 단점 | 10일 시연·검표·신 7위 같은 현 설계의 가정이 코드 곳곳(상수 14개, 페이즈 7개, 상태 필드 40개)에 박혀 있어 "조금 고친다"가 "다 뜯는다"가 되기 쉽다. 규칙이 코드에 있으니 디렉터가 못 읽는다 | 처음 짜는 비용. 해석기를 너무 일반적으로 만들면 디렉터가 못 읽는 "작은 언어"가 생긴다(범위를 못 박아야 함). 초기에는 테스트도 새로 |
| 밑바탕이 바뀌면 | 페이즈·자원·인물 수가 바뀌는 순간 엔진 절반을 다시 쓴다. **약함** | 페이즈 순서·자원 이름·사건 목록은 표 교체. 새 **동사**(예: 전투 방식 자체)가 추가될 때만 해석기 확장. **강함** |
| 어림 작업량 | **중**(엔진 수정 1,000줄 + game.js 흐름 800줄 + 데이터) | **대**(해석기 ~1,200줄 + 화면 ~1,000줄 + 표 설계 + 테스트) — 다만 두 번째 바뀜부터는 **소** |
| 맞는 경우 | Q1·Q2·Q4 답이 현 프로토타입과 70% 이상 겹칠 때 | 답이 아직 안 나왔거나, 나와도 몇 번 더 바뀔 것이 확실할 때(지금) |

**추천: B안.** 단, 범위를 못 박는다: 해석기가 다루는 것은 ①페이즈 순서표 ②자원·수치표 ③사건표(조건·선택지·판정·효과) ④인물표 ⑤지도(문자 격자) ⑥대사표 — 여섯 가지뿐. 그 밖의 특수 연출은 코드로 두고 "예외 목록"에 적는다. A안의 살릴 틀(dispatch·rng·normalize·테스트 골격·대화창·파이프라인)은 B안 안에서도 그대로 쓴다.

## 5. 새 밑바탕을 코드로 옮기는 흐름 (디렉터용)

1. 기반설계 부장이 설계 문서를 낸다 — 페이즈(하루의 순서), 자원, 인물, 사건, 지도, 결말 조건.
2. 우리는 그 문서를 **표**로 옮긴다. 표는 사람이 읽는 파일(JSON)이고, 디렉터가 열어 봐도 뜻이 보여야 한다.
3. 표 검사 스크립트가 "빠진 것·안 맞는 것"을 알려 준다. 이 단계에서 설계 구멍이 먼저 드러난다.
4. 엔진은 표를 읽어 "지금 할 수 있는 일"과 "한 뒤의 결과"만 계산한다. 그림·소리는 모른다.
5. 엔진이 돌면 봇이 200판을 돌려 "이기기 너무 쉬운가, 결정이 가짜인가"를 숫자로 낸다. 밸런스 디자이너가 표를 고친다.
6. 화면은 엔진이 준 상태를 그리고, 플레이어의 키·클릭을 `dispatch`로 넘긴다. 표현 부장의 규격(타일·초상·창 크기)을 여기서 받는다.
7. 아트는 Codex → `build_art.sh` → `v3/img`로 들어온다. 코드가 그림 이름을 부를 뿐, 그림 교체에 코드 수정은 없다.
8. 텍스트 에디터가 표의 문장을 고친다(코드 밖). 문장 검사가 길이·금지어·용어를 자동으로 잡는다.
9. `tools/verify.sh` 녹색 → 플레이테스트 1회 → 디렉터 승인 → `deploy.bat`.
10. 설계가 바뀌면 1~3만 다시 한다. 4·6은 새 "동사"가 생길 때만 손댄다.

## 6. 접점

**기반설계 부장과**
1. 표의 **스키마**(열 이름·값 범위)를 설계 문서와 함께 확정 — 사건표·인물표·페이즈표의 첫 줄을 같이 쓴다.
2. 수치·확률은 전부 표에 두기로 약속 — 코드에 "80부터 무너진다" 같은 상수를 다시 심지 않는다.
3. 봇이 볼 "판단 정보"(화면에 보이는 값)의 목록 — 봇은 그것만 보고 고른다. 이 목록이 곧 UX의 가시성 규칙.

**표현 부장과**
1. 규격표 1장: 타일·사람·초상·장면·아이콘 크기와 팔레트. `build_art.sh` 인자가 이 표에서 나온다.
2. 그림 이름 규칙(`종류/이름.png`)과 manifest — 코드는 이름만 부르고, 없으면 글자로 대신하는 현 방식 유지.
3. 대화창·무대 레이아웃(그림은 무대 층, 글은 상자)의 치수 — review_flow_ux.md 실측 기준으로 CSS 상수를 같이 정한다.
